# MUHOU 项目工程笔记

本文档用于记录当前系统的产品设计、工程边界、部署经验和可复盘的技术难点。后续上线后应继续更新为最终版。

## 1. 产品定位

MUHOU 是面向舞美道具租赁场景的小程序系统，核心角色包括租赁方、工厂方、管理员。系统围绕道具资产入库、审核、租赁下单、扫码出入库、评价、仲裁和资金结算形成闭环。

## 2. 角色与权限模型

- `demander`：租赁方，只能浏览已审核上架道具、维护方案、提交订单、支付、评价、发起仲裁。
- `supplier`：工厂方，只能管理自己名下道具、处理自己订单、扫码出库/归还、评价、发起仲裁。
- `admin`：管理员，只能访问审核、仲裁、运营管理等后台能力。
- 管理员账号同时拥有 `admin + supplier` 两条真实角色记录，但访问工厂视角时仍必须按当前 token/视角进行权限隔离。
- `demander` 与 `supplier/admin` 冲突，避免同一业务身份既下单又供货。

## 3. 核心业务闭环

1. 管理员生成工厂邀请码。
2. 新微信用户登录后选择工厂方，填写邀请码和工厂资料。
3. 管理员审核工厂入驻，通过后绑定 `supplier`。
4. 管理员生成小程序码，工厂扫码录入道具。
5. 道具进入待审核，管理员审核通过后自动上架。
6. 租赁方将道具加入方案，选择租赁起止日期、地址、使用场景和备注后提交订单。
7. 用户支付实际费用和押金，订单进入工厂待确认。
8. 工厂确认后进入待取货，逐件扫码出库。
9. 到期后逐件扫码归还，订单进入待评价。
10. 双方互评后订单完成并触发资金结算。
11. 若评价前发生争议，租赁方或工厂方可发起仲裁，管理员裁定后触发仲裁资金结算。

## 4. 资金流规则

下单支付：

- 用户向平台支付：实际费用 + 押金。

正常完成：

- 平台退还用户押金。
- 平台获得实际费用 20%。
- 工厂获得实际费用 80%。

用户仲裁工厂且管理员同意：

- 用户获得押金 + 从实际费用中扣出的赔付。
- 平台获得剩余实际费用的 20%。
- 工厂获得剩余实际费用的 80%。

工厂仲裁用户且管理员同意：

- 用户获得剩余押金。
- 平台获得实际费用的 20%。
- 工厂获得实际费用的 80% + 从押金扣出的赔付。

关键约束：

- 工厂向用户索赔上限为押金。
- 用户向工厂索赔上限为实际费用。
- 待仲裁订单不能继续评价完成，避免普通结算抢先发生。
- 资金流水使用 `order_fund_flow` 独立记录，避免只靠订单状态推断资金去向。

## 5. 关键安全边界

- 道具详情、仓库、订单、扫码出入库必须按当前 token 中的用户与角色判断，不信任前端传入角色。
- 工厂只能操作 `supplier_user_id = 当前用户` 的道具和订单。
- 管理员可查看审核/仲裁全局数据，但工厂视角仍不能越权操作其他工厂资产。
- 扫码出库/归还必须校验：二维码有效、道具属于当前订单、道具属于当前工厂、道具已审核、未下架、订单节点正确、未重复扫码。
- 扫码失败日志使用独立事务记录，避免业务异常回滚导致失败审计丢失。

## 6. 微信能力接入

- 微信登录：通过 `wx.login` 获取 code，后端调用 code2Session 换 openid 并绑定 `sys_user_wechat`。
- 手机号授权：企业主体小程序可通过微信接口换取手机号，替代短信验证码。
- 小程序码：管理员生成小程序码绑定 `prop_qr_code` 和预创建道具记录，工厂扫码进入录入页。
- 微信支付：当前已保留 JSAPI 支付、退款、分账的网关接口和 mock 实现。生产接入时需要商户号、API v3 key、商户证书/私钥、回调验签与解密、退款回调、分账接收方配置。

## 7. 数据库与 Flyway 经验

- 本项目使用 Flyway 管理数据库版本。
- 迁移文件一旦执行，不应直接修改历史 migration，否则会出现 checksum mismatch，导致后端启动失败并循环重启。
- 曾因服务器导入手工 SQL 后与 Flyway 历史不一致，导致 `flyway_schema_history` 中失败版本阻塞启动。
- 最终处理方式：本地整理为新的 baseline migration，服务器清空旧容器数据卷后重新部署，由 Flyway 一次性构建完整空表结构。
- 当前原则：已有部署不能改 `V1__baseline_schema.sql`，后续新增表/字段必须新建 `V2/V3...`。

## 8. Docker 部署经验

- 后端使用 Java 17 + Spring Boot 3.x，Docker 镜像内只需要 JRE/JDK 运行环境，不需要把 Maven 放进运行容器。
- MySQL 可试运行部署在同一台 Docker CE 服务器，生产增长后再拆到云数据库。
- Nginx 作为反向代理，对外暴露 80/443，将 `/api/` 转发到后端容器 `8078`。
- 小程序正式真机访问必须配置合法域名，不能直接使用未备案/未 HTTPS 的 IP 作为 request 合法域名。
- 文件不建议长期存服务器本地，正式应迁移到腾讯云 COS；本地 uploads 只适合开发或临时试运行。

## 9. 可包装的技术难点

- 多角色账号体系与 token 视角隔离，避免管理员切换工厂视角后污染前端状态。
- 道具二维码从“预生成空道具”到“工厂扫码填报”再到“管理员审核上架”的资产生命周期设计。
- 订单流程中按节点控制：待确认、待取货、租赁中、待评价、完成/驳回/仲裁。
- 出库/归还逐件扫码，配合订单明细状态，避免部分归还导致账务和库存不一致。
- 仲裁前置于评价完成之前，避免资金结算后再争议。
- 资金流拆分为订单支付、押金退款、平台佣金、工厂分账、仲裁赔付多条流水，便于后续对接微信支付、退款和分账。
- Flyway checksum、Docker 容器重启、MySQL 数据卷和线上 baseline 对齐，是部署阶段的重要工程经验。

## 10. 后续建议

- 引入 COS 文件服务，统一处理营业执照、道具图片、仲裁图片、小程序码图片。
- 接入微信支付真实回调、退款回调、分账回调，并增加通知日志表和对账任务。
- 接入学生认证或第三方教育身份认证能力，完善租赁方信用体系。
- 增加订单物流协商与补费用能力，避免线下物流费用争议。
- 增加管理员资金流水页面，按订单查看全部支付、退款、分账、赔付记录。
